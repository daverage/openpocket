# Bluetooth editor on the BlackBox

Research snapshot, 2026-11-23. The target is the OpenPocket editor and Stage view on Android Chrome, with a BlackBox as the first hardware target. This review uses existing hardware logs, local source, and public project records.

## Finding

Ettorebox, another OpenPocket fork, has already demonstrated the editor protocol over standard BLE MIDI on a BlackBox. The original OpenPocket repository still releases v42, and the Ettorebox work is available as open upstream PR #30. The PR reports eight editor connections during a roughly two-hour BlackBox session with music and a footswitch connected. That establishes feasibility on the hardware family. Our v76 radio failures and the current Android Chrome connection remain separate questions to test. [Upstream v42 release](https://github.com/isod89/openpocket/releases/tag/v42) · [Upstream PR #30](https://github.com/isod89/openpocket/pull/30) · [Ettorebox build 27](https://github.com/steponme82/ettorebox/blob/main/docs/BT-AUDIO-TEST.md#test-build-27-the-web-editor-over-bluetooth)

## Where our experiments stopped

| Stage | Evidence |
| --- | --- |
| Installed firmware | v82 Synth Track is a regular test-channel build. The BLE controller, host and diagnostic service are compiled into the separate `OP_BLE` image. The installed v82 has no BLE peripheral for the editor to discover. [Build switch](../../firmware/build.sh) · [BLE inclusion](../../firmware/openpocket.c#L601) |
| Advertising and connection | Earlier hardware tests saw a BlackBox advertise and connect. A Mac sent Program Change and Control Change, a Chocolate Plus switched blocks, and USB confirmed the pedal state. On a separate branch a Pocket X accepted Android MIDI, but sustained slider traffic caused audible crackling. The historical `ble-v41` document mixed branch behavior with release wording. Its status banner gives the release distinction. [BlackBox test](../BLE-TEST.md#found-on-hardware-the-link) · [Pocket X test](../BLUETOOTH.md) |
| Hardware stability | The v76 `bluetooth` branch reported 10 clean cold starts with the radio suppressed. With it enabled, most boots faulted or hung, even when the radio started before audio. Good boots advertised and heard scanners. One good run recorded no radio preemption in 12,179 audio IRQs, and an inspected crash had intact code bytes. The BLE image linked with about 17 KB of main RAM free. These findings narrow the fault to radio-enabled integration on that setup. They leave memory corruption, DMA, interrupt and task interactions, and power or RF initialization open. [v76 hardware experiment log](https://github.com/daverage/openpocket/blob/f6645f1/docs/research/BLUETOOTH-RADIO-FINDINGS.md#5-experiment-log-blackbox-one-pedal-normal-firmware-restored-after-each-series) |
| Editor protocol on the pedal | The test BLE MIDI parser discards SysEx and the GATT characteristic advertises notifications without sending replies. The editor uses SysEx for connection, state, presets and other operations. Even a stable connection that responds to a footswitch cannot answer the editor until both directions are implemented. [BLE MIDI parser](../../firmware/px_ble_midi.h#L10) · [GATT service](../../firmware/ble/ble_midi.c#L2) · [Editor protocol](../EDITOR-PROTOCOL.md) |
| Editor in the browser | The current editor requests Web MIDI with SysEx. The `bluetooth` branch contains a separate Web Bluetooth adapter for a proposed custom GATT service and host tests against the real editor protocol through simulated BLE. It has no editor Connect button wired to that adapter and the firmware does not expose that GATT service. The branch recorded requests around 160 bytes and replies up to 851 bytes, so the real transport needs fragmentation, flow control and disconnect handling. [Editor connection](../editor.js#L28) · [Browser adapter](https://github.com/daverage/openpocket/blob/5ed2c1b/docs/pxble.js) · [Host tests](https://github.com/daverage/openpocket/blob/5ed2c1b/tests/test_pxble.mjs) |

Earlier radio bring-up corrected a stack-guard conflict, a missing SDK CRC mutex initialization, radio trims and an HCI event-mask stub. The later cold-boot failures are distinct from those fixed problems. Our current RF glue uses saved calibration records when available and substitutes defaults for some missing records. The prior investigation notes that the replay table came from FM-1, with fallback records from Pocket X. That makes comparing actual BlackBox initialization and the calibration present on our unit worthwhile. It does not establish a calibration cause for the v76 crashes. [Bring-up notes](../BLE-TEST.md#found-on-hardware) · [RF initialization](../../firmware/ble/ble_rf.c) · [v76 research notes](https://github.com/daverage/openpocket/blob/f6645f1/docs/research/BLUETOOTH-RADIO-FINDINGS.md#4-other-peoples-work-read-and-what-it-says)

The owner's two photos show the same crash and its saved `LAST START FAILED` report. The recovery boot bypasses effects and skips Bluetooth. A separate logged failure froze and reset via the watchdog. [Fault handler](../../firmware/bsp/chip/fm1_irq.h#L119) · [Boot report](../../firmware/openpocket.c#L680) · [BLE safe boot](../../firmware/openpocket.c#L752)

**Photographed fault, November 23 at 08:50.** The panel reports `PC 01C67794`, `RETS 01C605FA`, `VEC 1`, `DBG 00000000`, `EMU 00000001`, uptime 1,262 ms and stage `FIRST 6 S`. Rebuilding historical commit `f063993` with `OP_BLE=1` and the repository toolchain reproduced the panel's `DSP CODE AT 020102B6` marker for `px_block_label`. The saved return address is exactly the instruction after `a_enc` calls `px_wet_run` on CPU0. The saved PC lands on the XOR for `e->wl_b ^ 1`, near the start of the delay and reverb lane routine. `EMU` bit 0 reports a misaligned access, while the instruction at the saved PC is an XOR with no memory operand. The photos therefore localize the failure to this call without identifying the access or what disturbed execution. The activity counters show zero because the diagnostic snapshot is updated from the main loop, which had yet to reach its counter update. A future register capture can check the engine pointer passed in `r0` and copied to `r13` against `g_eng` at `0x01C20000` in this build. [Historical audio caller](https://github.com/daverage/openpocket/blob/f063993/firmware/px_audio.h) · [Wet-lane routine](../../engine/px_dsp.c#L2883) · [Exception bit definitions](../HARDWARE-HANDBOOK.md#L146)

Our experiment still services software timers from the cooperative main loop. Ettorebox found that LE deadlines could be missed there and moved the relevant controller timers to its 10 kHz tick. It also found a self-deadlock from incorrect interrupt-context detection on the footswitch scanning path. Those are concrete comparisons for timing and hang diagnosis, with separate reproducers from our cold boots. Ettorebox credits the v42 audio callback ordering fix for its early crackles. Our newer tree already includes that fix, so it cannot by itself account for the remaining v76 failures. [Our timer implementation](https://github.com/daverage/openpocket/blob/f6645f1/firmware/ble/ble_os.c#L317) · [Ettorebox interrupt-context findings](https://github.com/steponme82/ettorebox/blob/main/docs/BT-AUDIO-TEST.md#test-build-28s-hang-at-bluetooths-start) · [Timer changes](https://github.com/steponme82/ettorebox/blob/main/docs/BT-AUDIO-TEST.md#test-build-38-the-librarys-timers-on-time) · [Audio ordering fix](https://github.com/daverage/openpocket/commit/cadcf9e)

## What upstream and other projects add

- **Original OpenPocket.** The live `main` ref still points to v42 commit `995c84b`, dated November 10. The successor Bluetooth work is upstream PR #30, open as of November 23, from `steponme82:bt-audio`. VinSpee’s earlier working BLE MIDI footswitch is recorded in issue #9. Pulling upstream `main` would leave the editor-over-BLE changes outside our tree. [Upstream commit](https://github.com/isod89/openpocket/commit/995c84b5df53aace5d83478e66e85b37d0fa4372) · [BLE discussion](https://github.com/isod89/openpocket/issues/9) · [PR #30](https://github.com/isod89/openpocket/pull/30)
- **Ettorebox.** Build 27 added SysEx reassembly, same-transport replies, bounded outgoing BLE notifications, and cleanup on disconnect. The report describes a first catalogue read around 20 seconds, with later connections benefiting from caching. An early iPhone editor session ended in a supervision timeout. Later work addressed transmit pool exhaustion under combined traffic and moved controller timer deadlines out of the loaded main loop. Build 38 is the longer BlackBox run. The sibling’s storage, editor and DSP changed since the common base, so the reusable reference is its radio integration and transport behavior. The full A2DP and multi-link build shortened delays and cut factory NAM models for space. There is no measured requirement for these cuts with a single BLE editor link. [Editor notes](https://github.com/steponme82/ettorebox/blob/main/docs/BT-AUDIO-TEST.md#test-build-27-the-web-editor-over-bluetooth) · [Transport commit](https://github.com/steponme82/ettorebox/commit/44f436a31dc4d6d56d82ab6c11bf1c18d8aa01be) · [Transmit pool and timer notes](https://github.com/steponme82/ettorebox/blob/main/docs/BT-AUDIO-TEST.md#test-build-37-room-in-the-le-transmit-pool) · [Hardware run and tradeoffs](https://github.com/isod89/openpocket/pull/30)
- **BlackboxEdit and mvave-blackbox-ble.** This is a second hardware precedent using Web Bluetooth directly on stock BlackBox firmware. It uses M-VAVE’s custom AE40 GATT service with AE41 writes and AE42 notifications. Its preset packets and commands belong to the stock editor. It is a reference for the Android browser experience and the vendor link, separate from OpenPocket’s editor SysEx. [BlackboxEdit](https://github.com/jvsobrinho/mvave-blackbox-edit) · [Stock protocol](https://github.com/jvsobrinho/mvave-blackbox-ble/blob/main/docs/ble_protocol.md)
- **Pocket-Onyx, Optimist and Melodee.** Pocket-Onyx offers a source-only BLE build on the related pedal hardware using Optimist’s stack. Its documented editor connection is USB. Melodee uses the same alternative stack on the FM-1 and documents per-unit calibration when factory records are missing. These are useful secondary references if the vendor stack remains unstable or calibration varies by unit. [Pocket-Onyx BLE build](https://github.com/28spawn/Pocket-Onyx#enabling-bluetooth-le-user-build-required) · [Optimist MIDI guide](https://github.com/w0ts/optimist/blob/main/docs/guide/midi-usb.md) · [Melodee calibration](https://github.com/keremimo/melodee/blob/main/docs/BLE_MIDI.md#calibration-and-persistence)

## When we pick this up

1. Compare the boot, radio, IRQ and timer code in PR #30 against our `bluetooth` branch. The first target is a single BLE MIDI peripheral link with clean cold boots, guitar audio under load, and reconnection. The older radio-off control and USB diagnostics give a way to track any recurrence. Keep the combined Bluetooth-audio and footswitch-central features outside this first test.
2. Use Ettorebox’s existing two-way SysEx transport as the reference for a small OpenPocket read-only milestone. A Chrome connection should identify the pedal, read one preset and receive a front-panel state change. A catalogue read, sustained traffic with the DSP busy, and disconnect/reconnect then distinguish basic connectivity from a usable editor. Test save or restore after confirming link authorization and flash behavior.
3. Verify the real Android phone and Chrome early. Ettorebox documents Android with a BLE-MIDI companion app when Chrome does not see the port, macOS with Audio MIDI Setup, and iPhone with MIDIWeb. The longer hardware report names MIDIWeb. Direct Android Chrome on this BlackBox is still open. If Chrome cannot see the paired MIDI port reliably or the companion step is too cumbersome, the existing custom-GATT prototype is a viable path on Android Chrome. It still requires the stable firmware link, the pedal-side characteristics, and a user-initiated browser connection from a secure origin. [Ettorebox connection guide](https://github.com/steponme82/ettorebox/blob/main/docs/MANUAL.md#the-web-editor) · [Chrome Web Bluetooth requirements](https://developer.chrome.com/docs/capabilities/bluetooth)
